# Bugboard

内网用的多项目报障台账。人在网页上提报、接单、确认；测试 Agent 和修复 Agent 用同一套状态机走 REST / MCP。数据在本机 SQLite，附件存在本地磁盘。

确认权只在原报障人。没有自助注册，没有邮件或即时通知，刷新列表就能看到最新状态。

## 使用手册

### 第一次打开

空库会进入首装页。填一个用户名和至少 6 位的密码，这个账号就是超级管理员，并直接进入项目列表。之后只有管理员能开户，登录页没有注册入口。

右上角头像菜单可以改自己的密码，或退出。改密码需要当前密码，新密码至少 6 位。

### 两种角色，不要混

账号角色决定能不能进管理后台、能不能打开全部项目。项目成员角色决定能不能改这一张单的状态。

| 账号角色 | 能看到什么 | 主要做什么 |
|------|------------|------------|
| 用户 | 被加进成员名单的项目 | 提报、补充材料、确认修复、打回、对「不属实」提异议或认可 |
| 管理员 | 全部项目 | 开户、建项目、分成员、管 API Key。要改报障状态，还得在该项目成员里是管理员 |
| 超级管理员 | 全部项目 | 管理员的全部能力，另外可以任命超级管理员，删除项目和报障 |

账号是管理员或超级管理员时，不必先成为成员就能打开项目。普通用户没被加进任何项目时，项目列表是空的，需要账号管理员在「成员」页分配。

项目成员只有两种：用户、管理员。网页上的接单、提交修复、标不属实、请产品经理确认、要求补充、撤回、改优先级、立即发布和登记代码变更，看的是这个项目成员角色，不看账号是不是管理员。账号管理员可以维护成员名单，但自己没被设成该项目的管理员时，详情里的处理动作是空的。

管理员级 API Key 不走成员表：在它能访问的项目上，一律当成项目管理员。只有超级管理员能创建、修改或删除管理员级 Key。账号管理员仍可创建用户级 Key。用户级 Key 不能做这些处理动作。API Key 只有用户级和管理员级，不能是超级管理员。

超级管理员可以改、禁用、删除其他超级管理员。普通管理员不能动超级管理员账号，也不能删除自己正在登录的账号。禁用后的用户不能再登录。改自己的密码或被管理员重置密码后，旧的登录会话失效；自己改密码的这一次会留下来。

从还没有项目角色的旧库升级时，会把当时账号是管理员或超级管理员的成员回填成项目管理员。这次回填只在加上角色列时发生，之后改过的项目角色不会在每次启动时被覆盖。升级后请在成员页核对一次。

### 界面怎么走

登录后落在 **项目** 列表。列表上方是 **待我处理**：只列出这个账号现在要处理的单，按项目分组，点一条进入该单。某个项目没有要你处理的单时，这里不显示该项目。没有待办时，这里只有一句「现在没有需要你处理的报障」。

每张项目卡片上显示哪些数字，看的是账号角色：

- 账号是管理员或超级管理员：看到 **待处理 / 待补充 / 待发布 / 待确认**，数字是整个项目。
- 账号是用户：只看到 **待补充 / 待确认**，看不到待处理、待发布。若此人不是该项目的项目管理员，这两项只计自己提交的。若此人已是该项目的项目管理员，这两项是整个项目的数量，芯片种类仍只有这两项。

点进项目后默认是报障列表。顶部可以切到别的项目。项目内有这些分区：

- **报障**：筛选、排序、新建。状态筛选项分成「进行中」和「终态」。进行中含待产品经理确认和待发布。
- **走查**：录完的走查先是草稿，人看完才变成报障。
- **汇总**：总数和各状态数量，以及最近 7 / 30 / 90 天的新建与流入趋势。
- **变更**：这个被测项目在 Git 上的代码变更和发布记录。和右上角「版本与更新日志」（Bugboard 自己的发版说明）不是一回事。能打开项目的人都能看；登记变更和发布要项目管理员。
- **成员**：仅账号管理员或超级管理员可见。可以把用户加进来，并指定项目角色是用户还是管理员。

报障列表可以按状态、优先级、提交人筛选，也可以搜标题或报障编号。表头可以排序。编号形如 `SOC251106001`：项目缩写 + 固定东八区的 `YYMMDD` + 当天序号（至少 3 位）。日期按 UTC+8 计算，不读 `TZ`。

点开一条报障，左侧是 **下一步**（只显示当前身份此刻能做的动作），右侧是正文、附件和时间线。时间线上的每次流转都带着操作人和说明。

### 提一张报障

在项目的报障页点 **新建报障**。这一屏分两步，都可以走：

1. **问问项目助理**（可选）。不确定功能有没有、入口在哪，先问。只回答，不改代码，也不替你提交。
2. **再写这张报障**。现象清楚就直接填标题、描述和优先级，然后提交。也可以等上面问完：判断是「建议报障」或「没有把握」时，点回答下方的 **整理并填入报障**。回答里的标题、描述和优先级会写进下方，不会直接提交，改完再交。附件建议留在附件旁边，有图再贴。判断是「已经有了」时一般不用建单；仍要记一笔，点 **仍要填入报障**。

回答还在生成时，填入按钮不会出现。

1. 标题用一句话写清现象。
2. 正文写环境、复现步骤、期望和实际结果。支持 Markdown：二级标题、空行分段、有序列表。
3. 选优先级。不选就是 P2。
   - **P1**：核心流程不可用、崩溃、错误结果、数据风险。
   - **P2**：能用，但行为不对或不稳定。
   - **P3**：不挡使用，偏界面、文案、交互。
4. 需要的话再加附件，然后提交。提交后会打开这张单的详情。

附件可以拖进来、从剪贴板粘贴图片，也可以用麦克风录音。新建时可以圈一张图并说一句，或录一段走查：走查会先拆成草稿，看完才变成多张报障。网页和 REST 上传单文件不超过 50MB，一张单最多 20 个。支持 png、jpg、jpeg、gif、webp、mp4、webm、mov、pdf、docx、xlsx、txt、md、zip，以及 mp3、wav、ogg、m4a。MCP 的 `stage_attachment` 单独限制为 8MB。配了 `ASR_BASE_URL` 和 `ASR_API_KEY` 时，录音可以走服务端转写；缺任何一个时，转写接口返回 `available: false`，不去调外部服务。

一条报障只写一个现象。这是现有功能坏了，不是要一个现在没有的能力。要一个现在没有的能力、而且标题、正文和附件里还没写已经和产品经理确认、报障人也不是项目资料里的产品经理时，修复侧应走 **请产品经理确认**，不要标成不属实。报障人就是产品经理时，信息不够就要求补充，够就直接做。后补的确认不算。现象不存在、没用对或配置问题，才标不属实。

### 状态怎么走

```text
待处理 → 修复中 → 待发布 → 待确认 → 已确认

待处理 ──接单──▶ 修复中 ──提交修复说明──▶ 待发布 ──发布成功──▶ 待确认 ──确认已修复──▶ 已确认
   │               │                        │                    │
   │               │                        │                    └──仍有问题──▶ 待处理
   │               │                        └──发布失败仍停在待发布
   │               │                        └──撤回修复提交──▶ 修复中
   │               │
   ├──请产品经理确认──▶ 待产品经理确认 ──可以做──▶ 修复中
   │                         └──不做，标为不属实──▶ 不属实
   ├──标为不属实──▶ 不属实 ──提出异议 / 撤回不属实──▶ 待处理
   │                  └──认可不属实──▶ 已认可
   │
   └──要求补充──▶ 待补充 ──补充材料──▶ 待处理
```

待发布表示修复已提交并 push，还没上到验收环境。默认情况下，发布成功后才进入待确认，原报障人才能确认或打回。API Key 提交的单，该项目的管理员也可以确认已修复；打回仍只有原报障人。项目可以在管理后台「行为」里关掉「发布成功后推进」，这时成功也留在待发布。发布失败时单仍停在待发布。项目管理员可以在待发布时 **撤回修复提交**，单回到修复中。验收只处理待确认。

| 动作 | 谁来做 | 从 | 到 | 说明 |
|------|--------|----|----|------|
| 接单（开始修复） | 项目管理员 | 待处理 | 修复中 | 可选 |
| 提交修复说明 | 项目管理员 | 修复中 | 待发布 | 必填。流程上应已 commit 并 push；服务端不检查 git，只校验身份、状态和说明。建议写成「原来的问题 / 现在的表现 / 请这样重测」 |
| 发布后待确认 | 项目管理员或发布任务 | 待发布 | 待确认 | 默认：一次成功发布把本批待发布推进到待确认。失败则仍停在待发布。行为里关掉推进后，成功也不改状态 |
| 确认已修复 | 原报障人；API Key 提交的单，项目管理员也可以 | 待确认 | 已确认 | 可选。已确认是终态。只对待确认，不要对待发布确认。人提交的单仍只有原报障人能确认 |
| 仍有问题 | 原报障人 | 待确认 | 待处理 | 必填，写仍失败的步骤 |
| 请产品经理确认 | 项目管理员 | 待处理、修复中 | 待产品经理确认 | 必填。要一个现在没有的能力，提交时还没写已经确认，且报障人不是项目资料里的产品经理 |
| 可以做 | 项目管理员 | 待产品经理确认 | 修复中 | 可选。只有人明确说可以做时才走 |
| 不做，标为不属实 | 项目管理员 | 待产品经理确认 | 不属实 | 必填。只有人明确说不做时才走 |
| 标为不属实 | 项目管理员 | 待处理、修复中 | 不属实 | 必填，写实际看到了什么、为什么对不上 |
| 提出异议 | 原报障人 | 不属实 | 待处理 | 必填 |
| 认可不属实 | 原报障人 | 不属实 | 已认可 | 可选。已认可是终态，不能再异议或撤回 |
| 撤回不属实 | 项目管理员 | 不属实 | 待处理 | 必填，写上次判错的地方 |
| 要求补充 | 项目管理员 | 待处理、修复中 | 待补充 | 必填。缺的是只有报障人能提供的材料 |
| 补充材料 | 原报障人 | 待补充 | 待处理 | 必填，可同时附截图或记录 |
| 撤回修复提交 | 项目管理员 | 待发布 | 修复中 | 必填 |

另外可以写 **补充说明**：不改状态，只写入时间线。项目管理员随时可以写。原报障人只有在待处理时可以写。这和「补充材料」（待补充 → 待处理）不是同一个动作。

「原报障人」是创建这张单的那个账号或那把 API Key。人代提的单，确认、打回、异议、认可不属实和补充材料也只有那个账号能做。API Key 提交的单，待确认时该项目的管理员也可以点确认已修复。别人打开详情时，下一步是空的，只能看时间线。

项目管理员可以在详情里改优先级。不合法的动作不会出现，不用去点灰色按钮。

带说明的流转都可以再挂附件，规则和新建时一样。说明同样支持 Markdown。

### 项目

管理员在项目列表点 **新建项目**。名称必填。缩写 2–8 位、字母开头、可含数字，例如 `SOC`；留空会按名称自动生成。缩写不能和已有项目相同，也不能互为前缀。说明会出现在项目列表卡片上。

项目标题旁可以有 logo（png、jpg、jpeg、webp，单张不超过 2MB，再传会替换）。没有 logo 时用文件夹图标。

项目标题旁的 **详情** 谁都能看。账号管理员可以改这些资料，Agent 接单和验收时会读它们：

- 产品经理、体验官
- 代码仓、默认分支、技术栈
- 设计稿、需求文档（链接，或直接上传文件，每种最多 20 个）
- 开发 / 测试 / 生产环境地址，以及默认验收环境
- 给 Agent 的说明（怎么启动、测哪些范围、账号向谁要）。不要在这里写密码、Token 或密钥

超级管理员可以删除项目。报障、附件和成员关系会一起删掉，不能恢复。删除单条报障同样只有超级管理员能做，附件和流转记录一并删除。

### 管理后台

顶栏 **管理后台** 只对账号管理员显示。打开后默认是数据分析，一共六页，顺序如下。

**数据分析。** 按提报人看一段时间内的提交量、被采纳量和各状态分布，可切全部 / 近 7 天 / 30 天 / 90 天。人和 API Key 分开统计。

**用户。** 创建账号时指定用户、管理员或超级管理员，并设初始密码。之后可以改角色、重置密码、禁用或删除。新用户要能提报，还得在对应项目的「成员」页加进去。要让他改报障状态，项目角色要设成管理员。

**API Key。** 给 Agent 用，不给人登录网页。明文只在创建或重新生成时出现一次，离开页面前复制备好。

- **用户级** 必须绑定至少一个项目，能力等同绑定项目里的普通用户。适合测试 Agent：提报、确认、打回、异议、补充材料。
- **管理员级** 默认可访问全部项目，只有超级管理员能创建、修改或删除。适合修复 Agent：接单、提交修复、标不属实、要求补充、改项目资料。

有效的 Key 可以改名称、角色和绑定项目，也可以重新生成（旧 Key 立刻失效）。禁用后可以再启用。删除是物理删除。已吊销的旧数据只能删除。列表里能看到前缀、最近使用时间和调用次数。

同一行可以复制两份接入配置：

- **本机 Agent**：在跑 Agent 的机器上起 `mcp/server.ts`，适合只支持本地命令的客户端。
- **远端 Agent**：`https://<服务地址>/mcp`，请求头 `Authorization: Bearer <API Key>`。支持远程 MCP 的客户端可以直接装，不用克隆本仓库。

**分派给 Agent。** 每个项目一套叫醒和发布配置。见下文「提交后分派给 Agent」和「夜间发布」。

**行为。** 每个项目一套协作开关，和「叫到哪台机器、发布命令」分开。管理后台「行为」页按项目列出已保存的配置摘要，可编辑；新项目点「新增」从待选项目里选一个再保存。默认是：网页、小组件、走查建单会叫醒，API Key 建单不叫醒；补充材料、仍有问题、异议、撤回不属实、待处理时的补充说明、以及人点「可以做」会再叫一次；叫醒后继续处理该项目其余待处理。管理员收件箱默认包含待处理、待产品经理确认、待发布、自己接手的修复中，待处理最多列 8 条。发布成功默认把待发布推进到待确认，执行中的任务默认 45 分钟没有回写算超时（可改成 5–180 分钟）。走查默认停顿超过 1.2 秒新开一条，不足 8 个字标成待确认，整理超过 8 分钟改用规则草稿。项目问答默认打开，每人每小时最多 20 次；关闭后新建报障时不能提问。没改过的项目用这套默认。

**提示词。** 两段现成提示词，填上目标项目名后复制到对话里。

- 用户级：按项目资料打开被测系统，把能复现的故障建成报障，并验收待确认的单。
- 管理员级：待处理的单先归类。现有功能坏了就修。要一个现在没有的能力、而且提交时还没写已经确认、报障人也不是项目资料里的产品经理，走请产品经理确认，不要标不属实。报障人就是产品经理时，信息不够就要求补充，够就直接做。

### 给 Agent 的最短闭环

准备两把 Key：用户级 `cursor-qa` 绑到目标项目，管理员级 `cursor-fixer`。在 Cursor 里用项目级 MCP 配置（不要把明文 Key 提交进仓库）：

```bash
cp .cursor/mcp.json.example .cursor/mcp.json
```

然后：

1. 测试 Agent：`create_bug`，记下返回的 `bugId`。
2. 修复 Agent：`start_fix`，改完并 push 后 `submit_fix`（说明必填，进入待发布），再用 `record_change`（`kind=fix`）记下这次修复。
3. 发布成功且该项目仍开着「发布后推进」时，单才进入待确认。测试 Agent 只验收待确认：通过就 `confirm_fix`，还有问题就 `reject_fix`。待发布还没上线，不要确认或打回。
4. 材料只在报障人手里时，修复 Agent 用 `request_info`；原报障人补上后用 `provide_info`，单回到待处理。要新能力又没有提交时的确认，用 `request_product`，不要 `mark_invalid`。

`create_bug` 可以带上 `stage_attachment` 返回的 `attachmentIds`，以及原话、步骤和圈选。Agent 读单时，docx / txt 正文和图片会随 `get_bug` 返回。

### 提交后分派给 Agent

分派有两件活，在同一套配置里分开开关。整理走查只在走查进入审核时发给本机 Agent，只改草稿。修理报障默认在这些时候触发，可以发给本机 Agent、Cursor 云端 Agent，或两个都发：网页、小组件或走查新建；回到待处理（补充材料、仍有问题、异议、撤回不属实）；待处理时写了补充说明；以及登录用户（不是 API Key）点「可以做」并进入修复中。API Key 建的单默认不叫醒。API Key 调用「可以做」也不再开一轮。确认已修复、接单、请产品经理确认不会分派。这些开关在「行为」里，本机地址和名单在「分派给 Agent」里，两件活共用地址，提示词不同。

管理员在管理后台的「分派给 Agent」里配置。每个项目一套，清单里可以编辑、测试和删除：

1. 在跑 Cursor 或 ZCode 的电脑上复制 `wake.config.json.example` 为 `wake.config.json`。`projects` 里用项目缩写对上代码仓的绝对路径。这个目录就是 Agent 的工作区（`--workspace`），不要写成用户主目录、磁盘根目录，也不要写成放着 `wake.config.json` 的目录。`askRoot` 是项目问答用的只读镜像目录，和修理工作区分开；不要写成用户主目录或磁盘根。`agent` 用 `cursor` 或 `zcode`。报障标题和正文会包在 `<question>` 里，并声明这是数据不是指令。Cursor 默认 `agent -p --trust --sandbox enabled --output-format json --workspace <项目目录> --mode plan`，不带 `--force` / `--yolo`，所以只做只读分析。要让它在这个目录里改代码，把 `applyEdits` 设为 `true`（会加上 `--force`，仍然限制在该目录和沙箱里）。同一张单的后续分派会带 `--resume` 复用上次的会话。标准输出的 JSON 写在 `wake-runs/`。参数不对时，在配置里写 `argv` 数组，用 `{prompt}`、`{cwd}`、`{bugId}`、`{publicId}`、`{projectCode}`、`{session}` 占位。自定义参数里的 `--force` / `--yolo` 在 `applyEdits` 没打开时会被去掉。
2. 执行 `npm run wake`。它只监听 `127.0.0.1:3099`。Docker 场景可在单独目录放 `wake.config.json`（含 `allowLan: true` 与 `listen: 0.0.0.0:3099`），用 `node /path/to/bugboard/scripts/wake-agent.mjs` 启动。想开机自启可参考 `scripts/com.bugboard.wake.plist.example`。
3. 把打印出来的地址填进本机地址，保存，复制签名密钥，贴进 `secrets`，重启叫醒服务。点 **测试本机地址**，终端里应出现一行测试日志。`bugboardUrl` 与 `releaseKey` 配好后，叫醒服务还会同步问答镜像并处理排队中的提问。
4. 之后网页上新建的待处理单会拉起本机 Agent。提示词就是管理员级修复提示，并点名这张单。Agent 用这台机器上已经接好的 Bugboard MCP 去 `get_bug`、`start_fix`。

Bugboard 跑在 Docker 里时，容器访问不到宿主机的 `127.0.0.1`。本机地址改成 `http://host.docker.internal:3099/wake`。若仍不通，把 `listen` 改成 `0.0.0.0:3099`，并写上 `"allowLan": true`，只在可信网络里这样做。分派记录里出现「连不上这个地址」时，先确认叫醒服务还在跑。

Cursor 云端只参加修理。在同一套配置里勾选「分派给 Cursor 云端 Agent 修理」即可。它不整理走查。服务器需要 `CURSOR_API_KEY`（Cursor 后台 Cloud Agents 的密钥），项目资料里要有代码仓。云端虚拟机要能访问 `BASE_URL`，单才会被回写；访问不了时，它仍按报障正文改代码，但不会自己 `submit_fix`。再设置 `BUGBOARD_DISPATCH_API_KEY`（一把管理员级 Key）后，云端 Agent 会带上这个站的远程 MCP。

同一张单、同一个原因，一分钟内只自动分派一次。详情页的 **再次分派去修理** 不受这限制。能手动分派的是待处理，以及刚从待产品经理确认进入修复中的单。这个按钮看的是账号管理员，不是项目成员角色。

### 夜间发布

发布在有代码仓的电脑上跑，不在 Bugboard 容器里跑。管理后台「分派给 Agent」里每个项目可以填三样：发布方式（默认 **不自动部署**；另有本机重启、云上部署）、发布命令、定时（`HH:MM`，留空则不参加定时）。`projects` 仍用项目缩写或 slug 对上绝对路径。`bugboardUrl` 指向 Bugboard，`releaseKey` 填一把管理员级 API Key。环境变量 `BUGBOARD_URL`、`BUGBOARD_RELEASE_KEY` 可以覆盖这两项。

紧急发布（网页「立即发布」或 MCP `run_release`）只入队。若该项目配了本机地址，叫醒服务会再拉起一次 `scripts/release-runner.mjs` 把队列领走。没配本机地址时，要等下面的 cron，或手动执行 `npm run release`。

Mac Studio 在 22:00 跑定时发布（路径按你的机器改）：

```cron
0 22 * * * cd /Users/你/Apps/bugboard && /绝对路径/node scripts/release-runner.mjs --schedule >> /Users/你/Apps/bugboard-wake/release.log 2>&1
```

`--schedule` 用固定东八区的当前 `HH:MM`（也可用 `--at=22:00` 指定）去对项目里的定时。只有发布方式是本机重启或云上部署、定时正好等于这个时刻、并且还有待发布报障或尚未挂上发布的代码变更，才会入队。然后领走队列：工作区必须是 git、origin 与代码仓一致、当前分支就是项目默认分支；只落后则快进，只超前则推送，两边都有新提交就中止。接着执行发布脚本，再回调。默认会把仍待发布的报障标成待确认；「行为」里关掉推进后，成功也留在待发布。工作区有未提交改动，或本地与远端已经分叉，会中止并记一条失败的发布，报障保持待发布。发布方式仍是「不自动部署」时，领走后直接记失败，不跑命令。

发布命令只能是一条绝对路径，不能有空格、管道或 shell。路径要落在 `/Users`、`/opt`、`/usr`、`/homebrew` 或该项目工作区里，文件名不能是 shell 或解释器（如 `bash`、`node`）。执行中的任务超过该项目的超时（默认 45 分钟）没有回写，会把这次分派记为失败，并在该项目的变更页写入一条失败的发布，原因是「发布任务超时未完成，已释放」，然后放开下一次入队。超时空跑发生在下一次入队或领取时，不是单独的计时器。

想让紧急发布在没开叫醒服务时也能很快被领走，可以另加一条每分钟的 `node scripts/release-runner.mjs`（不带 `--schedule`）。

工具权限、配置示例和冒烟脚本见 [`docs/mcp-examples.md`](docs/mcp-examples.md)。本机不依赖 Cursor 界面时，可以跑：

```bash
npm run mcp:smoke
```

## 安装与运行

本地开发（空库打开 http://127.0.0.1:3000 会进入首装）：

```bash
npm install
npm run dev
```

```bash
npm test
npm run build
# 生产启动（standalone，局域网）。npm start 只执行最后一行的 node，不会复制 public / static。
cp -R public .next/standalone/ && cp -R .next/static .next/standalone/.next/
DATA_DIR=./data SESSION_SECRET='换成强随机串，且不要用开发默认值' \
  HOSTNAME=0.0.0.0 PORT=3080 node .next/standalone/server.js
```

Docker 把主机 **3080** 映射到容器 **3000**，容器内监听 `0.0.0.0`。镜像里会复制 `public`、`.next/static` 和 `mcp/`，并以用户 `bugboard` 运行。数据目录在构建阶段就建好。局域网可直接访问：

```bash
docker compose up --build -d
```

- 本机：http://127.0.0.1:3080
- 局域网：http://\<主机局域网IP\>:3080

数据卷是 `bugboard-data`（容器内 `/data/db` 与 `/data/uploads`）。

| 变量 | 谁读取 | 说明 |
|------|--------|------|
| `SESSION_SECRET` | Web 进程 | Session cookie `bugboard_session` 的加密密钥。生产环境（`NODE_ENV=production`）未设置，或仍是开发默认值 `dev-only-session-secret-change-me-32chars!!` 时，启动会失败。代码不检查最短长度。未设置 `NODE_ENV` 的本地 `npm run dev` 会落到这个开发默认值 |
| `BUGBOARD_TRUST_PROXY` | Web 进程 | 设为 `1` 时，登录和上报限流才信任代理写上的地址：优先 `X-Real-IP`，否则取 `X-Forwarded-For` 最靠近代理的一段。未设置时忽略这些头，不按调用方自报的 IP 分桶 |
| `BASE_URL` | Web 进程 | 对外访问地址。API Key 页复制远端 MCP 地址时用它。Cursor 云端 Agent 也用它拼报障链接和 MCP。真实入口写在部署环境的 `BASE_URL` 里。compose 在没传入时回落到 `http://127.0.0.1:3080`，只适合本机 |
| `CURSOR_API_KEY` | Web 进程 | 可选。Cursor Cloud Agents 的密钥。项目启用了云端 Agent 才会用。未设置时云端分派记为跳过 |
| `BUGBOARD_DISPATCH_API_KEY` | Web 进程 | 可选。一把管理员级 Bugboard Key，只交给 Cursor 云端 Agent 的 MCP，不进网页 |
| `DATA_DIR` | Web 进程 | 数据根目录。未设置时是进程工作目录下的 `data`。Docker 里是 `/data` |
| `DB_PATH` | Web 进程 | SQLite 文件。未设置时是 `$DATA_DIR/db/bugboard.sqlite`。Docker 里是 `/data/db/bugboard.sqlite` |
| `UPLOADS_DIR` | Web 进程 | 附件目录。未设置时是 `$DATA_DIR/uploads`。Docker 里是 `/data/uploads` |
| `HOSTNAME` / `PORT` | Web 进程 | 监听地址和端口。Docker 内是 `0.0.0.0:3000`，compose 把主机 3080 转到容器 3000。远端 MCP 在进程内回连 REST 时用 `http://127.0.0.1:$PORT` |
| `TZ` | 容器 | compose 与镜像设为 `Asia/Shanghai`。报障编号和页面上的时间不读这个变量，代码里固定加 8 小时 |
| `ASR_BASE_URL` / `ASR_API_KEY` | Web 进程 | 可选。两个都有才启用转写，请求 `$ASR_BASE_URL/audio/transcriptions`。缺一则只存录音 |
| `ASR_MODEL` | Web 进程 | 可选。转写模型名，默认 `whisper-1` |
| `BUGBOARD_AGENT_FILES` | 本机 MCP | 可选。`get_bug` 把附件落到这个目录再抽正文。未设置时用仓库下 `data/agent-files` |
| `BUGBOARD_BASE_URL` / `BUGBOARD_API_KEY` | 本机 MCP | `mcp/server.ts` 调用 REST 用。`BUGBOARD_BASE_URL` 默认 `http://127.0.0.1:3000` |
| `BUGBOARD_QA_KEY` / `BUGBOARD_FIXER_KEY` / `BUGBOARD_PROJECT_ID` | `npm run mcp:smoke` | 冒烟脚本用。可写在 `.env.mcp.local`。项目 ID 缺省是 `3` |
| `BUGBOARD_URL` / `BUGBOARD_RELEASE_KEY` | 发布 runner | 覆盖 `wake.config.json` 的 `bugboardUrl`、`releaseKey`。URL 缺省 `http://127.0.0.1:3080` |
| `WAKE_LISTEN` / `WAKE_AGENT` / `WAKE_CWD` | 叫醒服务 | 覆盖 `wake.config.json` 的 `listen`、`agent`、`cwd`。监听缺省 `127.0.0.1:3099`，agent 缺省 `cursor` |
| `WAKE_ALLOW_LAN` | 叫醒服务 | 设为 `1` 时允许非本机监听，等同配置 `allowLan: true` |
| `WAKE_APPLY_EDITS` | 叫醒服务 | 设为 `1` 时允许改文件，等同 `applyEdits: true` |
| `WAKE_SECRET` | 叫醒服务 | 追加一把签名密钥，与配置文件里的 `secrets` 并列 |

`NEXT_TELEMETRY_DISABLED` 只在镜像构建和运行阶段写死为 `1`，不是业务配置。

需要公网时，在 `Apps/nginx` 给这个服务加反代和证书。本仓库只负责 Web、API、MCP 和数据。这个 nginx 目录不在本仓库里。
