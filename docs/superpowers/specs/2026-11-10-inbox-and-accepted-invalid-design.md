# 登录待办与认可不属实 — Design

## Goal

登录后打开项目首页，第一眼看到这个账号此刻要处理的报障。清单按项目分组，点一条进入该单。不属实在原报障人点「认可不属实」之前一直留在待办里；点之后进入终态「已认可」。

## 已认可

状态键 `acknowledged`，界面文案「已认可」。`bugs.status` 无 CHECK 约束，不改表结构。已经是不属实、还没人点过的旧单保持不属实。

| 动作 | 从 | 到 | 谁 | 说明 |
|------|----|----|----|------|
| `accept_invalid` 认可不属实 | 不属实 | 已认可 | 原报障人 | 可不填 |
| `dispute_invalid` 提出异议 | 不属实 | 待处理 | 原报障人 | 必填，不变 |
| `reopen_invalid` 撤回不属实 | 不属实 | 待处理 | 管理员 | 必填，不变 |

已认可没有出边。不能异议，管理员也不能撤回。要再查就新开一张单。

谁能点：创建这张单的用户或那把 Key，沿用 `isReporter`。管理员看别人的不属实单，仍然只有「撤回不属实」。网页上「认可不属实」与「确认已修复」一样，点一下就提交，不进必填说明表单。详情页按钮仍由现有的 `allowedActions` 生成。MCP 增加与 `confirm_fix` 同形的工具 `accept_invalid`。

认可不叫醒修复端。异议打回待处理，仍按现有规则叫醒。

列表筛选、项目汇总、管理后台统计各自单列「已认可」。确认率分子仍只是已确认。已采纳仍是修复中 + 待确认 + 已确认。已认可不进这两项。

用户级 Agent 只有在人明确说「这张认可不属实」时才调用 `accept_invalid`。自己复测觉得不成立时保持不属实。管理员级 Agent 不调用该动作；已认可与已确认一样只查看。`list_bugs` 的 status 增加 `acknowledged`。

## 待办里有什么

网页会话只服务登录用户。匹配范围是该用户能进的项目。

原报障人（`reporter_type = user` 且 `reporter_id` 是当前用户）看到自己的：

| 状态 | 行上的下一步 |
|------|----------------|
| 待确认 | 确认修复是否有效 |
| 不属实 | 认可，或提出异议 |
| 待补充 | 补充材料 |

管理员（含超级管理员）另外看到能进的项目里全部待处理，以及**自己**最后一次把它推进「修复中」的单。推进人取该单最新一条 `to_status = 'fixing'` 的事件；操作者必须是当前用户。修复 Agent 的 Key 接的单不进任何网页用户的待办。没有这条事件的修复中单也不进待办。

别人的待确认、待补充、不属实不进管理员待办。管理员自己提的单和上面三行放在同一清单里，不另开一栏。一张单只出现一次：管理员提的待处理单按待处理显示，不重复。

网页上报记在入口所属管理员名下，因此那个人要确认、认可或补充的单会出现在他的待办里。挂在 API Key 上的单不出现在网页用户的个人待办里。

## 首页

位置：`/projects` 顶部，项目网格之上。登录仍然进这个页，不加路由，不加顶栏角标。

有待办时：

- 标题「待我处理」，旁边是总条数。总条数含被折叠的待处理。
- 其下按 `listProjects` 的顺序分组。某个项目在这个账号下没有任何待办单时，待我处理里不显示该项目。下面的项目列表仍列出全部可见项目。
- 组标题是项目名，副行只写出本组有的种类和条数，条数是该种类的全部张数，含被折叠的待处理。例如「待确认 1 · 不属实 2 · 待处理 12」。
- 每一行是整行链接，去 `/bugs/{id}`。行内有优先级、报障编号、标题、状态徽章、上表里的下一步文案。
- 组内顺序：待确认、不属实、待补充、修复中、待处理。同一种里 P1、P2、P3，再按 `updated_at` 新的在前。
- 待确认、不属实、待补充、修复中全部列出。每个项目的待处理最多列出 8 条，其余收成一行「其余 N 条待处理」，链到 `/projects/{id}/bugs?status=pending`。

没有待办时，同一位置只留一句「现在没有需要你处理的报障」。下面的项目网格、现有数量芯片、创建项目保持原样。芯片口径不改：管理员看到的待确认和待补充仍是整个项目的数量。

数据由服务端在渲染项目页时查出，不单独发客户端请求。点进已删除的单时，沿用详情页现有的找不到处理。

## 查询

新增 `listInbox(identity)`，返回按项目分组的条目。普通用户只查自己的待确认、不属实、待补充。管理员在此之外再查可见项目的全部待处理，以及修复中且最后推进人是自己的单。项目可见性走现有的 `listAccessibleProjectIds`。

## 还要改到的表面

状态枚举、`STATUS_LABEL`、状态徽章、汇总图、管理后台统计、报障筛选、状态排序权重，都要认识 `acknowledged`。新增 `--status-acknowledged`：沿用现有徽章（文字 + 浅底），颜色与已确认、不属实都分开。README 与 `PRODUCT.md` 里的状态句子补上「已认可」。

## 测试

- 原报障人可 `accept_invalid`，说明可空；管理员、其他用户、其他状态都不行。
- 已认可上 `dispute_invalid` 与 `reopen_invalid` 都失败。
- `accept_invalid` 不叫醒；`dispute_invalid` 仍叫醒。
- 普通用户的待办只有自己的待确认、不属实、待补充。
- 管理员的待办含全部待处理、自己推进的修复中、自己作为报障人的三行；不含别人的待确认、待补充、不属实，也不含 Key 接的修复中。
- 已认可不出现在待办里，确认率分子和已采纳都不含它。
- 一个项目的待处理超过 8 条时，待办只展开 8 条；总条数、组副行和「其余 N 条」都用全量。

## 不做

- 独立待办页、顶栏角标、待办 MCP 工具
- 改项目卡片芯片的统计口径
- 已认可之后的撤回或再异议
- 邮件、站内实时通知
