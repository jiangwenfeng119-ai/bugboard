Bugboard 是内网多项目报障台账：提报 → 判定/修复 → 原报障人确认。本文说明 **Bugboard 产品本身** 的用法；各被测项目在 Git 上的改动请见项目内的 **变更** Tab（与右上角菜单里的「版本与更新日志」不是一回事）。

### 用户怎么用

1. 登录后从 **项目** 进入你有权限的项目，在 **报障** 中新建单：标题、正文、优先级，并可拖拽/粘贴图片、录音或上传附件。
2. 在 **我的报障** 或报障详情里跟进状态：**待处理** → **修复中** → **待确认** → **已确认**；也可能被标为 **不属实**。
3. **待确认** 时你是唯一可以点 **确认修复** 或 **打回** 的人；打回后单回到 **待处理**。
4. 若被标 **不属实**，可 **提出异议**（回到待处理）或 **认可不属实**（终态 **已认可**）。
5. 修复方可能向你 **请求补充信息**；在详情里回复即可。

### 管理员怎么用

管理员除用户能力外，还可：

1. 在 **管理后台** 创建账号、项目、分配成员、管理 API Key。
2. 在任意项目中 **分拣**、**接单**、写修复说明或 **标不属实**；查看全项目汇总与趋势。
3. 为项目配置修复 Agent、发布仓库路径与夜间发布；在需要时用 **紧急发布** 插队。
4. 打开项目 **变更** Tab，查看该被测项目在 Git 上的 fix/feature/release 账本（由 Agent 经 MCP 写入，不是 Bugboard 产品 changelog）。

### 待发布与夜间发布

修复 Agent **提交修复**（`submit_fix`）后，单进入 **待发布**，不会立刻变成 **待确认**。含义：代码已 push，但尚未部署到你验收的环境。

- **夜间发布**（默认）：调度在约定窗口（如 22:00）对队列执行 sync → 部署 → 将对应单批量迁入 **待确认**，便于次日验收。
- **紧急发布**：管理员可对选中单触发即时发布管道（与夜间同一套流程），只适合必须马上验的场景。
- 发布失败时单会留在 **待发布**，汇总与项目页会提示，需处理后再发。

修好必须先 **commit 并 push**；发布与 push 分离，避免未同步代码被部署。

### 项目「变更」Tab 与产品更新日志

| | 项目 **变更** Tab | 用户菜单 **版本与更新日志** |
|--|-------------------|---------------------------|
| 记录谁 | 被测项目（如业务系统）在 GitHub 上的改动与发布 | **Bugboard 报障系统** 自己的发版说明 |
| 谁维护 | 修复/开发 Agent（MCP `record_change`）与发布任务 | 产品维护者更新仓库内 `CHANGELOG.md` |
| 入口 | 项目页 **变更** | 顶栏头像 → **版本与更新日志**（`/changelog`） |

产品手册（本页）与版本日志面向所有已登录用户；管理后台使用同一顶栏菜单。
